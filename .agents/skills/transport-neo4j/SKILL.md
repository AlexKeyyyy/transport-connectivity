# Neo4j как производная проекция

Прочитай GraphSnapshot/GraphEdge контракт. Если смысл ребра или сценария не определён,
сначала используй `$transport-graph-methodology`. PostgreSQL остаётся источником истины.

## Модель и запросы

Согласуй реальные labels, relationship types и стабильные ключи с моделью. Не
используй внутренний elementId как постоянный ID проекта. MERGE-ключи защищай
подходящими uniqueness constraints; повторная выгрузка не добавляет дубликаты.
Связи могут иметь время, длину, транспорт и ID версии как свойства. Промежуточный
узел нужен по семантике/идентичности, а не из-за количества свойств связи.

До выполнения выясни server edition/version, Cypher language и наличие GDS.
Для проектной схемы без БД работай по файлам и явно укажи отсутствие live-проверки.
Не включай Cypher 25/Enterprise/APOC по умолчанию. Параметризуй значения, проверяй
план через EXPLAIN; PROFILE исполняет запрос, в том числе запись.

## Версии и GDS

Не смешивай снимки в одной аналитической проекции. Для общего City сохраняй
принадлежность вершин GraphSnapshot отдельно: фильтра одних рёбер недостаточно,
особенно для изолированных вершин. Проверяй состав ID, количество и направление
вершин/рёбер относительно PostgreSQL.

Проверь совместимость сервера, GDS plugin и Python client по официальной таблице.
Оцени память перед крупной проекцией/расчётом, выбери корректную orientation и weight.
Сначала проверь алгоритм на маленьком эталоне. Сохраняй результат с AnalysisRun
в PostgreSQL; named GDS graph освобождай по завершении своей работы. Не удаляй
чужие проекции и не затирай старый успешный снимок незавершённым импортом.

В PR укажи версии, команды, исходный snapshot, баланс объектов и реальные проверки.
Если сервера нет, результат — проект/код без заявления об успешной интеграции.
