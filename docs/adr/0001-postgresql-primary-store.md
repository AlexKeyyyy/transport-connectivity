# ADR 0001. PostgreSQL/PostGIS — основное хранилище, Neo4j и Elasticsearch — производные

Статус: принято. Дата: 13 ноября 2026 года. Задача: [#4](https://github.com/AlexKeyyyy/transport-connectivity/issues/4).

## Контекст

Проект использует три хранилища: реляционное с пространственными данными, графовое
и поисковое. Если данные можно менять в каждом из них, версии расходятся и результат
анализа невозможно воспроизвести.

## Решение

- Источник истины — PostgreSQL с PostGIS: метаданные снимков, нормализованные города и
  измерения, версии графа и результаты расчётов. Ограничения PK/FK/UNIQUE/CHECK
  проверяет база.
- Neo4j получает одну версию графа (`graph_snapshot`) отдельной командой выгрузки.
  Результаты графовых расчётов возвращаются в PostgreSQL вместе с `analysis_run`.
- Elasticsearch получает индекс городов отдельной командой. Его недоступность не влияет
  на загрузку и анализ.
- Обе проекции можно удалить и пересобрать из PostgreSQL без потери данных.
- Большие исходные файлы хранятся вне базы и Git; база хранит их SHA-256 и manifest.

## Рассмотренные варианты

- Хранить граф только в Neo4j: удобно для алгоритмов, но связь со снимками, отчётами
  загрузки и пространственными запросами пришлось бы дублировать, а целостность
  проверять вручную.
- Работать с файлами CSV без базы: достаточно для одного прогона, но не даёт ограничений
  целостности, пространственных индексов и совместного доступа к версиям.

## Последствия

- Выгрузка в Neo4j и Elasticsearch — отдельные шаги после успешной загрузки; частично
  собранная проекция не объявляется готовой.
- Любой показатель в отчёте прослеживается: `metric_result` → `analysis_run` →
  `graph_snapshot` → входные `data_snapshot` и конкретные `load_run` их загрузки.
- Подробности — в [архитектуре](../architecture.md).
