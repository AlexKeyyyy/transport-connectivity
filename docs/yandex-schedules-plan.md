# План: прямые рейсы из Яндекс Расписаний

Статус: **проект**, сбор не начат. Документ отвечает, какие данные о рейсах нужны графу,
как получить их при суточной квоте ключа и сколько это займёт. Ограничения API — в
[constraints.md](constraints.md#яндекс-расписания).

## Зачем

«Если быть точным» даёт время поездки между любыми двумя городами, в том числе с
пересадками, и считает его по средней скорости. Для анализа устойчивости нужны
**непосредственные связи** ([ADR 0003](adr/0003-measurement-vs-graph-edge.md)): есть ли
прямой поезд или самолёт из города A в город B и сколько таких рейсов. Тогда можно задать
вопрос «что будет со связностью, если отменить рейсы через узел X».

Результат сбора — для каждой упорядоченной пары наших городов и вида транспорта
(`train`, `plane`): число прямых рейсов на выбранную дату и минимальное время в пути.
Как превратить это в ребро графа, решает методика графа, а не этот сбор.

## Почему не перебором пар

Метод `search` отвечает на вопрос об одной паре. Для 180 городов это 32 220 запросов на
вид транспорта, то есть 65 дней квоты в 500 запросов. Сбор строим наоборот: от станций.
Запрос `schedule` по станции возвращает все её рейсы, а `thread` по рейсу — все его
остановки. Один поезд Москва — Владивосток даёт сразу все пары наших городов на маршруте.

## Шаги

| Шаг | Метод | Что получаем | Запросов (оценка) |
|---|---|---|---|
| 0 | Кабинет разработчика | Фактическая квота ключа | 0 |
| 1 | `stations_list` | Все станции России с кодами и координатами (~40 МБ) | 1 |
| 2 | — (локально) | Соответствие наш город → населённый пункт Яндекса | 0 |
| 3 | — (локально) | Список станций: вокзалы (`train`) и аэропорты (`plane`) этих городов | 0 |
| 4 | `schedule` на дату D | Отправления каждой станции, `uid` рейсов | 400–700 |
| 5 | `thread` на дату D | Остановки каждого уникального рейса | 2 000–5 000 |
| 6 | — (локально) | Пары наших городов на каждом рейсе → прямые связи | 0 |

**Шаг 2 — сопоставление городов.** По координатам, а не по названию: ближайший
населённый пункт Яндекса со станциями в радиусе 15 км от точки города. Название
используется только для проверки. Неоднозначные и далёкие совпадения идут в файл
ручной сверки. Результат — внешний ID города в пространстве имён `yandex_rasp`
(таблица `city_external_id`, [модель данных](data-model.md)).

**Шаг 3 — станции.** В первой версии только `train` и `plane`. Электрички (`suburban`)
и автобусы дают на порядок больше отправлений и страниц ответа, поэтому откладываются.
Это заметное ограничение для городов Подмосковья из нашего набора (Мытищи, Химки,
Подольск и другие): их связь с Москвой держится в основном на электричках.

**Шаг 4 — отправления.** Дата D — один будний день, на две–три недели вперёд от даты
сбора, одна для всех запросов. Страница — до 100 рейсов, у крупных вокзалов Москвы
и Санкт-Петербурга будет несколько страниц.

**Шаг 5 — остановки.** Каждый `uid` запрашивается один раз (`uid` может меняться,
поэтому берём его из ответов шага 4 того же сбора). Поезд, проходящий через несколько
наших городов, встретится в расписании каждого из них, но запрашиваем его один раз.

**Шаг 6 — связи.** Для рейса с остановками в наших городах `A, B, C` (в порядке
следования) прямые связи — `A→B`, `A→C`, `B→C`. По всем рейсам считаем число рейсов
и минимальное время для каждой пары. Ключ рейса — `uid` нитки + дата отправления +
станции посадки и высадки; это закрывает вопрос уникальности из
[#15](https://github.com/AlexKeyyyy/transport-connectivity/issues/15).

## Сколько это займёт

Оценки шагов 4–5 — **оценки**: до шага 1 неизвестно, сколько у 180 городов вокзалов
и аэропортов и сколько рейсов через них проходит. Порядок величины: 3 000–6 000
запросов, то есть **6–12 дней** при 500 запросах в сутки. После шага 1 и шага 4 на
нескольких станциях оценка уточняется по фактическим числам, и только потом
планируется полный сбор.

Как уложиться быстрее, не нарушая условий API:

- **Сначала самолёты.** В «Если быть точным» авиаизмерения есть только у 130 из 180 городов, а рейсы в основном без промежуточных посадок — это меньшая и самостоятельная часть.
- **Потом поезда**, начиная с городов с наибольшим числом железнодорожных пар.
- **Запросить у Яндекса увеличение квоты** для учебного проекта, если оценка выйдет за сроки.

## Как собираем

- Каждый ответ сохраняется как есть в `data/raw/yandex_rasp_<D>/` вместе с параметрами запроса; сбор продолжается с места остановки на следующий день и не тратит квоту на уже полученные ответы.
- Счётчик запросов за сутки (уже есть в пилотном скрипте) не даёт превысить квоту.
- Manifest снимка: дата D, дата сбора, число запросов по методам, SHA-256 файлов.
- Нормализация — по тем же правилам, что и для «Если быть точным»: отсутствие рейса, отсутствие запроса и ошибка API различаются; частичный сбор не публикуется как готовый.
- В материалах и на графиках — указание «Яндекс Расписания» как источника (условие API).

## Ограничения результата

- Один день D — это снимок, а не типичная неделя: у части рейсов расписание по дням недели. При необходимости добавляется второй день.
- Связь «есть прямой рейс» не говорит о вместимости и цене.
- Города без вокзала и аэропорта получают связи только через «Если быть точным».
- Без электричек и автобусов связность Подмосковья занижена.
