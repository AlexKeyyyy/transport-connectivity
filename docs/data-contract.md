
# Контракт данных: полный CSV связности и нормализованный выход

Версия контракта: `1.0-draft`. Статус: стратегия идентификации зафиксирована — единственный внешний ключ Sber ID, автоматический fallback на ОКТМО не применяется. Row-level правила подтверждены на срезе 270 строк. Проверка полноты и однозначности Sber ID, а также проверка конфликтов атрибутов на полном CSV ещё не выполнены.

Контракт описывает один шаг: внешний CSV «Если быть точным» → `cities.csv`, `route_measurements.csv`, `rejected_rows.csv`, `run-report.json`.
**Вне охвата.** Пилотные файлы `data/samples/cities.csv` (OSM) и `data/samples/route_measurements.csv` (OSRM), дорожные сегменты и Яндекс Расписания. Это другие источники с другими ключами. Имена выходных файлов совпадают с пилотными, поэтому выход пишется в отдельный каталог `data/normalized/<snapshot_id>/`.

| Источник | «Если быть точным», набор `intercity_connectivity`, версия публикации 2026-06-29, CC BY 4.0 |
| Файл | `data_intercity_connectivity_162_v20260629.csv` (из ZIP) |
| Формат | UTF-8, разделитель `;`, первая строка — заголовок, 22 поля |
| Объём по документации | 96 660 записей |

Ожидаемый размер сходится с матрицей без диагонали: 96 660 = 180 × 179 × 3 (180 городов, 3 вида транспорта). Это проверка на здравый смысл, а не правило. Фактическое число городов определяется по файлу (раздел 7).

**Manifest** лежит рядом с файлом и содержит: URL источника, версию, SHA-256 ZIP и CSV, размер в байтах, число записей, список 22 колонок в порядке файла.

**Проверка до чтения данных.** Если не совпал SHA-256, точный заголовок (имена и порядок 22 колонок) или число записей из manifest, запуск завершается со статусом `failed`. Выход не создаётся. UTF-8 BOM в начале файла допускается: он снимается перед сравнением заголовка, факт наличия BOM пишется в `run-report.json`.

**Чтение.** Все 22 колонки читаются как строки (`csv` или `all_varchar`). Автоопределение типов запрещено: оно ломает ОКТМО с ведущими нулями и превращает ID в float.

## 2. Идентичность City

Название города никогда не ключ.

**Основной и единственный ключ источника** — Sber ID (`sber_territory_id_*`). Автоматический fallback на ОКТМО не применяется. ОКТМО сохраняется как отдельный внешний атрибут города, но не становится `source_city_id`. Если Sber ID отсутствует, строка отклоняется с `city_identity_missing`. OSM ID не подставляется и не выдумывается.

Для каждого города фиксируются пространство имён и значение:

| `id_namespace` | `source_city_id` |
|---|---|
| `sber_territory` | исходное значение Sber ID |

**Внутренний ID** воспроизводим на одном и том же входе:

```
NAMESPACE_CITY = de98ebe7-8f16-5a7f-b476-6c58b1f92076
               = uuid5(NAMESPACE_URL, "urn:transport-graph:namespace:city")
city_id        = uuid5(NAMESPACE_CITY, "<id_namespace>:<source_city_id>")
```

Константа фиксируется навсегда. Случайный UUID на каждый запуск не используется.

**Хранение внешних ID.** Sber ID и ОКТМО хранятся строками, ровно как в файле. Преобразование в int или float запрещено, ведущие нули сохраняются. Допустима только обрезка пробелов по краям; их число попадает в отчёт.

**Конфликты соответствий.** Город определяется по всему входному снимку, а не по отдельной строке. Проверяются:

- один Sber ID с несколькими ОКТМО;
- одно ОКТМО с несколькими Sber ID;
- расхождения названия, региона, населения и координат для одного Sber ID.

Правило разрешения конфликтов:

- **Конфликт Sber ID ↔ ОКТМО.** Если один Sber ID связан с несколькими ОКТМО **либо** одно значение ОКТМО связано с несколькими Sber ID, поле `oktmo` устанавливается в `NULL` для всех затронутых городов. Все конфликтующие соответствия записываются в `identity.oktmo_conflicts`. Строки измерений не отклоняются: Sber ID остаётся стабильным ключом.
- **Конфликт атрибута** (название, регион, население, координаты для одного Sber ID): применяется правило большинства, описанное ниже.
- **Отсутствие Sber ID** у города: все строки с этим городом отклоняются с `city_identity_missing`.

**Сбор значений атрибутов.** Значения атрибутов собираются из обоих концов всех входных CSV-записей (`from` и `to`) для соответствующего Sber ID. Каждое непустое валидное вхождение учитывается один раз. Порядок обработки строк не влияет на результат.

**Правило большинства для атрибутов города.** Перед выбором значения выполняется проверка его формата и допустимого диапазона. Невалидные значения исключаются из голосования и учитываются в `identity.invalid_attributes`. Правило большинства применяется только к валидным непустым значениям. Если валидных значений нет либо ни одно значение не набирает строго более 50% голосов, атрибут записывается как `NULL`.

- Для числовых полей (`population`) сравнение выполняется после преобразования в `integer`.
- Для текстовых полей (`name`, `region`) сравниваются значения после обрезки пробелов без изменения регистра и внутреннего содержимого.
- Для координат `latitude` и `longitude` сравнение выполняется по паре `(latitude, longitude)`; подробности ниже.

В `identity.attribute_conflicts` фиксируются все валидные непустые варианты атрибута и количество их появлений. Невалидные значения фиксируются отдельно в `identity.invalid_attributes` и в голосовании не участвуют.

**Валидация атрибутов города.** Атрибуты города валидируются на уровне города, а не строки:

- `population`: целое ≥ 0. Невалидное значение исключается из голосования, запись в `identity.invalid_attributes`. Если валидных значений нет — `NULL`.
- **Координаты — единая пара.** `latitude` — конечное число в диапазоне −90…90 включительно. `longitude` — конечное число в диапазоне −180…180 включительно. Для каждого вхождения рассматривается пара `(latitude, longitude)`. Строка с отсутствующей или невалидной хотя бы одной координатой в голосовании не участвует; факт пишется в `identity.invalid_attributes`. Правило большинства применяется к валидным парам. Если валидной пары с большинством нет, `latitude` и `longitude` в `cities.csv` одновременно устанавливаются в `NULL`. Измерения маршрутов при этом не отклоняются.

**Включение в `cities.csv`.** Включаются все города с определённым Sber ID, встретившиеся в любых входных строках, включая города, все измерения которых отклонены по другим причинам. Города без Sber ID не включаются.

## 3. Измерение

Одна запись — направленное измерение: `from_city_id → to_city_id` для одного `transport_type`. Прямое и обратное направление независимы, симметрию не достраиваем.

**Единицы.**

- `distance_m`: метры, `distance_km × 1000`.
- `duration_sec`: секунды, `distance_hr × 3600`.
- Пересчёт идёт через `Decimal`, не через float. Округление не применяется.
- Десятичный разделитель во входе — точка. Запятая считается невалидным числом (проверяем в разделе 7).

`duration_sec` остаётся оценкой по средней скорости, как и `distance_hr` в источнике. Расписанием поездки оно не является.

**Формат decimal в выходе.** Значения `distance_m`, `duration_sec`, `cities.latitude`, `cities.longitude` пишутся в нормализованном виде:

- без экспоненты;
- без trailing zeros после десятичной точки;
- без завершающей десятичной точки, если дробная часть нулевая.

Примеры: `Decimal('694.0') * 1000` → `694000`; `Decimal('9.8') * 3600` → `35280`; `Decimal('123.456') * 1000` → `123456`; `Decimal('123.4567') * 1000` → `123456.7`. Это обеспечивает байт-в-байт воспроизводимость.

**Происхождение строки.** `source_row_number` — номер физической строки исходного файла, с которой начинается CSV-запись. Первая строка заголовка имеет номер 1, поэтому первая запись данных обычно начинается с физической строки 2. Если поле в кавычках содержит перевод строки, у записи сохраняется номер физической строки её начала. `rows_read` в балансе — число CSV-записей, а не физических строк. Одна CSV-запись входа превращается не более чем в одну запись выхода или одну запись `rejected_rows.csv`.

**Идентификатор измерения.**

```
NAMESPACE_MEASUREMENT = 3df2f4b5-a23f-5ed3-8ea1-7d25fe8ea191
                      = uuid5(NAMESPACE_URL, "urn:transport-graph:namespace:measurement")
measurement_id        = uuid5(NAMESPACE_MEASUREMENT,
                              "<snapshot_id>|<from_city_id>|<to_city_id>|<transport_type>")
```

**Допустимые значения.** `transport_type` ∈ {`road`, `rail`, `air`}, иначе отклонение `unknown_transport_type`. `from_city_id = to_city_id` — отклонение `self_pair`.

## 4. Пропуски и ошибки

Три разных состояния, их не смешиваем:

| Состояние | Признак во входе | Что делаем |
|---|---|---|
| Измерение есть | `distance_km` и `distance_hr` заполнены и оба являются допустимыми положительными числами | Запись попадает в `route_measurements.csv`. `missing_reason`, если заполнен, сохраняется дословно и сам по себе не делает строку ошибочной |
| Числового измерения нет (по данным источника) | `distance_km` и `distance_hr` пусты, `missing_reason` заполнен | Запись попадает в `route_measurements.csv` с `distance_m = NULL`, `duration_sec = NULL`. Это факт, а не ошибка. Не утверждаем, что маршрута точно нет: причина указана источником |
| Ошибка во входе | Заполнено только одно из двух числовых полей; оба пусты без `missing_reason`; числовые значения невалидны; либо нарушены другие проверки | Строка отклоняется, причина в `rejected_rows.csv` |

Причины отклонения:

| Код | Когда |
|---|---|
| `invalid_number` | Значение не разбирается как число, отрицательное, ноль или не конечное |
| `partial_measurement` | Заполнено только одно из `distance_km` / `distance_hr`, независимо от его валидности |
| `missing_without_reason` | Оба значения пусты, `missing_reason` пуст |
| `unknown_transport_type` | `transport_type` не в {`road`, `rail`, `air`} |
| `self_pair` | `from_city_id = to_city_id` |
| `city_identity_missing` | Нет Sber ID у одного из городов |
| `exact_duplicate` | См. раздел 5 |
| `key_collision` | См. раздел 5 |

**Порядок проверок и приоритет `reject_reason`.** Проверки выполняются в следующем порядке; первая ошибка определяет `reject_reason`, все ошибки строки попадают в `detail`:

1. `city_identity_missing` — нет Sber ID у from- или to-города.
2. `unknown_transport_type`.
3. `self_pair`.
4. Числовые поля: `missing_without_reason` → `partial_measurement` → `invalid_number`.
5. После прохода по всем строкам — `exact_duplicate` / `key_collision` среди прошедших первичную валидацию строк (раздел 5).

**`missing_reason` хранится дословно.** Поле не используется как самостоятельный признак ошибки и не должно автоматически приводить к отклонению строки, если оба измерения валидны. В проверенном срезе значение `CD` встречается вместе с заполненными `distance_km` и `distance_hr`; для строк без чисел встречается `Маршрут не найден`, а в `source` — `ND`. Расшифровки кодов (`CD`, `ND` и других) контракт не придумывает. Все различные значения с числом строк записываются в `run-report.json`. Смысл кодов добавляется только после подтверждения источником.

**Пустая строка и trim.** Пустая строка во входе читается как `NULL` в нормализованных полях. Пробелы по краям обрезаются для всех полей перед разбором и сравнением. В выходные текстовые поля (`name`, `region`, `missing_reason_raw`, `source_raw`, `comment_raw`) записывается значение после обрезки; внутренние пробелы сохраняются. `raw_json` сохраняет исходные значения без обрезки.

### Nullable входных полей

| Поле | Nullable | Правило |
|---|---|---|
| `city_from`, `city_to` | Да | Названия не ключи; при отсутствии `cities.name = NULL` |
| `region_from`, `region_to` | Да | При отсутствии `cities.region = NULL` |
| `oktmo_from`, `oktmo_to` | Да | Строковые атрибуты; отсутствие не заменяется вычисленным значением |
| `sber_territory_id_from`, `sber_territory_id_to` | Да во входе | Ключ; если отсутствует, строка отклоняется с `city_identity_missing` |
| `is_capital_from`, `is_capital_to` | Да | Не переносятся в нормализованный выход; сохраняются в CSV-снимке и `raw_json` |
| `population_from`, `population_to` | Да | Если заполнено, должно быть целым числом не меньше нуля |
| `lat_from`, `lon_from`, `lat_to`, `lon_to` | Да | Валидность проверяется парой; невалидная или отсутствующая хотя бы одна координата → обе `NULL` в `cities.csv` |
| `transport_type` | Нет | Допустимы только `road`, `rail`, `air` |
| `distance_km`, `distance_hr` | Да | Оба заполнены — измерение; оба пусты с `missing_reason` — числового измерения нет; частичное заполнение отклоняется |
| `missing_reason`, `source`, `comment` | Да | Сохраняются дословно; коды не расшифровываются без подтверждения источника |

**Правило частичной ошибки.** Отклонённые строки не останавливают запуск: они учитываются, а статус становится `success_with_rejections`. Запуск считается `failed`, если не прошла проверка раздела 1, не сошёлся баланс из раздела 6 или случилась непредвиденная ошибка. Выход пишется во временный каталог и переносится в `data/normalized/<snapshot_id>/` целиком только при успехе. Частичный набор не публикуется. Допустимую долю отклонений определяем после первого прогона на полном файле.

## 5. Повторы

Ключ записи: `(from_city_id, to_city_id, transport_type)` внутри снимка.

**Что считается значениями измерения.** Значения измерения — это `(distance_m, duration_sec, missing_reason_raw)`. Поля `source_raw` и `comment_raw` описывают пояснение источника и не являются частью измерения. Различия в `source_raw`/`comment_raw` при совпадающих значениях измерения не приводят к `key_collision`; они фиксируются в `run-report.json` (`duplicates.source_differences`).

Обработка выполняется группировкой всех строк, прошедших первичную валидацию раздела 4, по ключу.

- Если все строки группы совпадают по значениям измерения, сохраняется одна строка группы, остальные отклоняются с `exact_duplicate`. Различия в `source_raw`/`comment_raw` не мешают этому считаться точным повтором; они попадают в `duplicates.source_differences`.
- Если в группе присутствуют разные значения измерения, все строки группы отклоняются с `key_collision`, включая точные повторы внутри этой группы.
- Строки с ошибками первичной валидации в группировку не включаются.

**Первой считается строка с минимальным `source_row_number`.** Это правило применяется независимо от внутреннего порядка обработки и обеспечивает детерминированный выбор сохраняемой записи.

Примеры.

1. Ключ A → B, road, две строки: (1) 100 км, 2 ч, `missing_reason = CD`, `source = OSM`; (2) 100 км, 2 ч, `missing_reason = CD`, `source = OSRM`. Значения измерения совпадают; сохраняется строка с минимальным `source_row_number`, вторая отклоняется с `exact_duplicate`, различие `source` фиксируется в `duplicates.source_differences`.

2. Ключ A → B, road, три строки: (1) 100 км, 2 ч; (2) 100 км, 2 ч; (3) 120 км, 2 ч. В группе разные значения измерения; все три строки отклоняются с `key_collision`.

3. Ключ A → B, road, две строки: (1) числа есть, `missing_reason = CD`; (2) числа есть, `missing_reason = ND`. Значения измерения различаются (`missing_reason_raw` разный); обе строки отклоняются с `key_collision`.

## 6. Выход

Каталог: `data/normalized/<snapshot_id>/`. Формат: UTF-8, разделитель `,`, перевод строки `\n`, заголовок в первой строке, кавычки по необходимости. `NULL` — пустое поле. Все тексты из источника пишутся после обрезки пробелов по краям.

**Порядок записей детерминирован:**

- `cities.csv` по (`id_namespace`, `source_city_id`) как строки;
- `route_measurements.csv` и `rejected_rows.csv` по `source_row_number`.

### `cities.csv`

| № | Колонка | Тип | NULL | Примечание |
|---|---|---|---|---|
| 1 | `city_id` | uuid | нет | UUID5, раздел 2 |
| 2 | `id_namespace` | text | нет | Всегда `sber_territory` |
| 3 | `source_city_id` | text | нет | Значение Sber ID |
| 4 | `oktmo` | text | да | Строка; `NULL` при неоднозначности |
| 5 | `name` | text | да | Не ключ |
| 6 | `region` | text | да | |
| 7 | `latitude` | decimal | да | Градусы, WGS84; нормализованный decimal |
| 8 | `longitude` | decimal | да | Градусы, WGS84; порядок осей для геометрии (долгота, широта), SRID 4326 |
| 9 | `population` | integer | да | Человек |

### `route_measurements.csv`

| № | Колонка | Тип | NULL |
|---|---|---|---|
| 1 | `measurement_id` | uuid | нет |
| 2 | `snapshot_id` | text | нет |
| 3 | `source_row_number` | integer | нет |
| 4 | `from_city_id` | uuid | нет |
| 5 | `to_city_id` | uuid | нет |
| 6 | `transport_type` | text | нет |
| 7 | `distance_m` | decimal | да, если числового измерения нет |
| 8 | `duration_sec` | decimal | да, если числового измерения нет |
| 9 | `missing_reason_raw` | text | да |
| 10 | `source_raw` | text | да |
| 11 | `comment_raw` | text | да |

### `rejected_rows.csv`

`source_row_number`, `reject_reason`, `detail`, `raw_json`.

- `detail` — строка с пояснением: `field=value` для первой ошибки; при нескольких ошибках — через `; `.
- `raw_json` — JSON-объект с 22 ключами в порядке файла; значения — строки как во входе, пустая строка сохраняется как `""`; сериализация компактная, UTF-8, без ASCII-эскейпинга.

### `run-report.json`

| Блок | Содержимое |
|---|---|
| `contract_version`, `snapshot_id`, `status` | `success`, `success_with_rejections` или `failed` |
| `input` | Путь, SHA-256, размер, число прочитанных CSV-записей, наличие BOM, проверка заголовка |
| `output` | Число строк и SHA-256 файлов `cities.csv`, `route_measurements.csv` и `rejected_rows.csv`. Сам `run-report.json` в перечень хешируемых выходных файлов не включается |
| `balance` | `rows_read = route_measurements + rejected_rows`. Если не сходится, статус `failed` |
| `rejections` | Число строк по каждому коду причины |
| `missing_reason_values` | Различные значения дословно, с числом строк |
| `duplicates` | Число `exact_duplicate` и `key_collision`; `source_differences` — ключи, где совпали значения измерения, но отличались `source_raw`/`comment_raw` |
| `identity` | Заполненность Sber ID и ОКТМО по концам строк и по уникальным городам; число городов по пространствам имён; `oktmo_conflicts`; `attribute_conflicts`; `invalid_attributes` |
| `service` | Время начала и конца, длительность, пиковая память, версия кода (commit) |

**Воспроизводимость.** Повторный запуск на том же входе даёт байт-в-байт одинаковые `cities.csv`, `route_measurements.csv`, `rejected_rows.csv`. В `run-report.json` могут отличаться только поля блока `service`. Тест: сравнить SHA-256 трёх файлов после двух запусков.

## 7. Проверки на полном файле до перевода контракта в 1.0

Полный набор проверок выполняется на исходном CSV из публикации (96 660 записей). Срез 270 строк не заменяет полный файл. Результаты проверок полного файла записываются в таблицу, и только затем контракт переводится из `draft` в `1.0`.

```sql
-- DuckDB
CREATE VIEW t AS SELECT * FROM read_csv('data_intercity_connectivity_162_v20260629.csv',
  delim=';', header=true, all_varchar=true);
```

| № | Что проверить | Запрос или способ | Результат |
|---|---|---|---|
| 1 | Число записей и городов | `SELECT count(*) FROM t;` и число различных Sber ID по объединению `_from` и `_to` | |
| 2 | Заполненность Sber ID | `SELECT count(*) FROM t WHERE coalesce(trim(sber_territory_id_from),'')='' OR coalesce(trim(sber_territory_id_to),'')='';` | |
| 3 | Однозначность Sber ID ↔ ОКТМО | Sber ID с несколькими ОКТМО и наоборот: `GROUP BY ... HAVING count(DISTINCT ...) > 1` по обеим сторонам (from и to) | |
| 4 | Один город — одни атрибуты | Расхождения `city/region/population/lat/lon` внутри Sber ID, объединив `_from` и `_to` | |
| 5 | Десятичный разделитель и формат чисел | Значения `distance_km`, `distance_hr`, содержащие `,` или не разбирающиеся как число | |
| 6 | Значения `missing_reason` | `SELECT missing_reason, count(*) FROM t GROUP BY 1;` | |
| 7 | Пустые значения без причины | Строки, где `distance_km` и `distance_hr` пусты, а `missing_reason` пуст | |
| 8 | Дубликаты | Повтор ключа `(sber_from, sber_to, transport_type)`, точные и с расхождениями; отдельно — где различаются только `source`/`comment` | |
| 9 | Формат ОКТМО | Распределение длин (8 или 11 знаков), ведущие нули | |
| 10 | Переводы строк внутри кавычек | Проверить CSV-парсером физические номера начала записей; `wc -l − 1` не считать надёжным числом записей при многострочных полях | |

### 7.1. Предварительная проверка среза 270 строк

Файл `city_from;...txt` содержит заголовок из 22 полей и 270 CSV-записей. Это фрагмент данных, а не полный файл из 96 660 записей. По нему получены следующие результаты:

| Проверка | Результат на срезе |
|---|---|
| Число записей | 270 |
| Число различных городов | 10 |
| `transport_type` | `road` — 90, `rail` — 90, `air` — 90 |
| Заполненность Sber ID | Во всех 270 записях оба Sber ID заполнены |
| Формат ОКТМО | Во всех проверенных значениях 11 символов |
| Десятичный разделитель | Запятых в `distance_km` и `distance_hr` не обнаружено; заполненные значения используют точку |
| Измерения с числами | 180 записей; у всех `missing_reason = CD` |
| Числового измерения нет | 90 записей: оба числовых поля пусты, `missing_reason = Маршрут не найден`, `source = ND` |
| Частично заполненные измерения | 0 |
| Пустые измерения без причины | 0 |
| Повторяющиеся ключи `(sber_from, sber_to, transport_type)` | Не обнаружены в этом срезе |
| Пустые значения Sber ID | Не обнаружены в этом срезе |

**Важное следствие для правил обработки.** В исходном варианте контракта измерение считалось валидным только при пустом `missing_reason`, а заполненный `missing_reason` при числовых значениях приводил к `reason_with_value`. Это противоречит приложенным данным: все 180 строк с числовыми измерениями содержат `missing_reason = CD`. Поэтому правило исправлено: если `distance_km` и `distance_hr` заполнены и валидны, строка принимается как измерение, а `missing_reason` сохраняется без интерпретации.

Файл `route_measurements.csv` проверен отдельно и относится к другому формату: 90 строк данных и 9 колонок (`from_city_id`, `from_city`, `to_city_id`, `to_city`, `distance_m`, `duration_sec`, `router`, `calculated_at`, `data_version`). Это пилотный нормализованный файл OSRM, а не входной CSV «Если быть точным»; использовать его для проверок раздела 7 нельзя.

Результаты выше относятся только к срезу. Они не подтверждают количество городов, заполненность идентификаторов, отсутствие конфликтов и дубликатов или формат всех значений в полном наборе.

### 7.3. Синтетические тесты логики

Эти тесты проверяют правила, которые не проявляются на срезе 270 строк, но зафиксированы в контракте. Это тесты логики processor, а не утверждение, что такие случаи есть в полном CSV. Для каждого теста — минимальный искусственный вход и ожидаемый результат.

| № | Сценарий | Ожидание |
|---|---|---|
| S1 | Один Sber ID встречается с двумя разными ОКТМО | `cities.oktmo = NULL`; соответствия в `identity.oktmo_conflicts`; строки измерений не отклоняются |
| S2 | Одно значение ОКТМО встречается у двух разных Sber ID | `cities.oktmo = NULL` у обоих городов; соответствия в `identity.oktmo_conflicts` |
| S3 | Два равных по частоте значения `region` для одного Sber ID | `cities.region = NULL`; оба варианта в `identity.attribute_conflicts` |
| S4 | Для одного Sber ID `population`: 3 невалидных значения и 1 валидное `100000` | Валидное значение выбирается; `cities.population = 100000`; невалидные в `identity.invalid_attributes` |
| S5 | Один маршрут, одинаковые числа и `missing_reason_raw`, разные `source_raw` и `comment_raw` | Сохраняется строка с минимальным `source_row_number`; вторая получает `exact_duplicate`; различия фиксируются в `duplicates.source_differences` |
| S6 | Один маршрут, разные числа (`100` / `120`) | Обе строки в `rejected_rows.csv` с `key_collision`; в `route_measurements.csv` записи нет |
| S7 | Один маршрут, одинаковые числа, разные `missing_reason_raw` (`CD` / `ND`) | Обе строки в `rejected_rows.csv` с `key_collision`; записи нет |
| S8 | У города `latitude` валидна, `longitude` отсутствует | В `cities.csv` `latitude = NULL` и `longitude = NULL`; `identity.invalid_attributes`; строки измерений не отклоняются |
| S9 | Группа из трёх строк: (1) 100/2ч, (2) 100/2ч, (3) 120/2ч | Все три строки в `rejected_rows.csv` с `key_collision`; записи нет |
| S10 | Строка с пустым Sber ID | `rejected_rows.csv` с `city_identity_missing`; город в `cities.csv` не попадает |

## 8. Что контракт не решает

- Связь с OSM ID: отдельный crosswalk после этого релиза.
- Построение рёбер графа: `RouteMeasurement` остаётся измерением поездки между городами, а не ребром `GraphEdge`.
- Допустимая доля отклонённых строк: определяется после первого прогона полного CSV.
- Расшифровка кодов `missing_reason` (`CD`, `ND` и других): только после подтверждения источником.
- Автоматический fallback с Sber ID на ОКТМО: не включён.
- Перенос `is_capital_*` в нормализованные таблицы: отдельное изменение контракта, если понадобится.
- Приоритет источников для конфликтующих атрибутов города сверх правила большинства: отдельное решение команды.
- Объединение с OSRM `route_measurements.csv`, OSM `road_segments_sample.geojson` и `public_transport_sample.json`: другие источники и семантика.
