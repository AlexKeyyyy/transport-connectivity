# Модель данных

Исходный и нормализованный слои реализованы в миграциях PostgreSQL/PostGIS (#27).
Аналитический слой описан ниже для следующих этапов.
Правила разбора CSV «Если быть точным» (ID, единицы, пропуски, отклонения) — в контракте
данных ([data-contract.md](data-contract.md), версия `1.0-draft`); модель им следует
и не повторяет их. Контракт описывает выходные CSV обработчика, модель — таблицы, в
которые они загружаются: например, `cities.oktmo` из CSV становится записью
`city_external_id` с пространством имён `oktmo`.

Схемы: [данные](diagrams/data-model.svg) и [граф и анализ](diagrams/graph-model.svg)
([исходники](diagrams/README.md)). Компоненты и потоки — в [архитектуре](architecture.md).

## Главное

Данные проходят три слоя, каждый следующий получается из предыдущего:

| Слой | Вопрос, на который отвечает | Основные таблицы |
|---|---|---|
| Исходный | Откуда и когда взяты данные, что отклонено при проверке | `data_snapshot`, `load_run` |
| Нормализованный | Какие есть города и сколько стоит поездка между ними | `city`, `city_external_id`, `route_measurement` |
| Аналитический | Какой граф построен и что посчитано на нём | `graph_snapshot`, `graph_edge`, `analysis_run`, `metric_result` |

Пять решений, на которых держится модель:

1. **У каждой записи известно происхождение.** Город, измерение и ребро графа ссылаются
   на снимок источника (`data_snapshot`), а снимок — на файл с контрольной суммой.
   Любое число в отчёте можно проследить до строки исходного файла.
2. **Город определяется кодом, а не названием.** Ключ — UUID, вычисленный из Sber ID;
   ОКТМО, OSM и коды Яндекса хранятся рядом с указанием источника
   ([ADR 0002](adr/0002-city-identity.md)). Одноимённые города не склеиваются.
3. **Измерение — не ребро графа.** `route_measurement` — то, что сообщил источник;
   `graph_edge` — то, что методика решила включить в граф. Из одних измерений можно
   построить разные версии графа и сравнить их ([ADR 0003](adr/0003-measurement-vs-graph-edge.md)).
4. **«Маршрута нет» не равно нулю.** Если источник не нашёл маршрут, расстояние и время —
   `NULL`, а причина сохраняется дословно. Ноль означал бы мгновенную поездку.
5. **PostgreSQL — источник истины.** Neo4j и Elasticsearch — производные копии, их можно
   удалить и пересобрать ([ADR 0001](adr/0001-postgresql-primary-store.md)).

## Соглашения

- Ключи воспроизводимы: `uuid` версии 5 из внешнего кода, поэтому повторная загрузка
  того же снимка даёт те же ключи и не создаёт дубликатов.
- Единицы: расстояние в метрах, время в секундах, тип `numeric` — перевод из км и часов
  точный. Время событий — `timestamptz` в UTC.
- Координаты — `geometry(Point, 4326)`, порядок (долгота, широта). Расстояния в метрах
  считаются через `geography`, а не в градусах.
- Списки значений (вид транспорта, статус) — `text` с `CHECK`: их легче расширить.
- Каждый внешний ключ проиндексирован; пространственные поля — индексом GiST.

В таблицах ниже: **PK** — первичный ключ, **FK** — внешний ключ, **UK** — уникальность;
«да» в колонке NULL — поле может быть пустым.

## Исходный слой

### data_snapshot — снимок источника

Один скачанный и проверенный файл или ответ API. Сам файл лежит в `data/raw/` вне Git,
в базе — его описание.

| Поле | Тип | NULL | Смысл и ограничения |
|---|---|---|---|
| snapshot_id | text | нет | PK, например `tochno_intercity_v20260629` |
| source_id | text | нет | FK → `data_source` — справочник источников: код (`tochno_intercity`, `osm`, `osrm_public`, `yandex_rasp`), название, лицензия |
| retrieved_at | timestamptz | нет | Когда получен |
| file_name | text | нет | Имя файла без абсолютного пути |
| sha256 | text | нет | UK; хеш байтов файла — доказывает, что анализ сделан на этом файле |
| record_count | integer | да | Число записей |
| manifest | jsonb | нет | URL, версия, кодировка, колонки |

### load_run — запуск обработки снимка

Отчёт одного прогона обработчика. Неуспешный прогон сохраняется для диагностики,
но его данные не публикуются.

| Поле | Тип | NULL | Смысл и ограничения |
|---|---|---|---|
| load_run_id | uuid | нет | PK |
| snapshot_id | text | нет | FK → `data_snapshot` |
| contract_version, code_commit | text | нет | По какому контракту и каким кодом обработано |
| status | text | нет | `running`, `success`, `success_with_rejections`, `failed` |
| rows_read, rows_written, rows_rejected | integer | да | Баланс: `rows_read = rows_written + rows_rejected` |
| started_at, finished_at | timestamptz | нет / да | |

Отклонённые строки хранятся в `rejected_row`: номер строки файла, код причины из
контракта и исходная запись без изменений.

## Нормализованный слой

### city — город

| Поле | Тип | NULL | Смысл и ограничения |
|---|---|---|---|
| city_id | uuid | нет | PK; `uuid5(NAMESPACE_CITY, 'sber_territory:<Sber ID>')` |
| name | text | да | Название; не ключ |
| region | text | да | Субъект РФ |
| population | integer | да | `>= 0` |
| location | geometry(Point, 4326) | да | Центр города; индекс GiST |
| attributes_snapshot_id | text | нет | FK → `data_snapshot`, откуда взяты атрибуты |

### city_external_id — внешние коды города

У одного города может быть Sber ID, ОКТМО, OSM-объект и код Яндекса. Каждый код
хранится вместе с пространством имён, поэтому одинаковые числа из разных систем не путаются.

| Поле | Тип | NULL | Смысл и ограничения |
|---|---|---|---|
| id_namespace | text | нет | PK (1/2): `sber_territory`, `oktmo`, `osm`, `yandex_settlement` |
| external_id | text | нет | PK (2/2); строкой, с ведущими нулями (`15701000001`, `node/1686293227`) |
| city_id | uuid | нет | FK → `city`; `UK (city_id, id_namespace)` |
| snapshot_id | text | нет | FK → `data_snapshot`, откуда соответствие |

Ключ `(id_namespace, external_id)` не даёт привязать один код к двум городам.

### route_measurement — измерение поездки

Направленное наблюдение источника: «из A в B таким видом транспорта — столько метров
и секунд». Строка CSV связности даёт одну запись.

| Поле | Тип | NULL | Смысл и ограничения |
|---|---|---|---|
| measurement_id | uuid | нет | PK; `uuid5` от снимка, пары городов и вида транспорта |
| snapshot_id | text | нет | FK → `data_snapshot` |
| source_row_number | integer | нет | Строка исходного файла; `UK (snapshot_id, source_row_number)` |
| from_city_id, to_city_id | uuid | нет | FK → `city`; города разные |
| transport_type | text | нет | `road`, `rail`, `air` |
| distance_m | numeric | да | Метры, `> 0`; `NULL` — маршрута нет |
| duration_sec | numeric | да | Секунды, `> 0`; оценка источника, не расписание |
| missing_reason_raw, source_raw, comment_raw | text | да | Пояснения источника дословно (`CD`, `Маршрут не найден`, `OSM`, `ND`) |

Ограничения: одна запись на `(snapshot_id, from_city_id, to_city_id, transport_type)`;
расстояние и время либо оба заданы, либо оба `NULL`; пустое измерение без причины
отклоняется ещё при обработке.

## Аналитический слой

Методика графа (что считать ребром, какой вес) ещё не утверждена. Модель хранит любую
выбранную версию графа и не выбирает методику за неё.

### graph_snapshot — версия графа

| Поле | Тип | NULL | Смысл и ограничения |
|---|---|---|---|
| graph_snapshot_id | uuid | нет | PK |
| methodology_version | text | нет | Версия методики, по которой построен граф |
| parameters | jsonb | нет | Виды транспорта, вес, пороги |
| is_directed | boolean | нет | Направленный ли граф |
| status | text | нет | `building`, `ready`, `failed`; анализ — только по `ready` |
| code_commit | text | нет | |

Какие снимки вошли в версию, хранит `graph_snapshot_input` (версия графа ↔ снимок, плюс
конкретный `load_run`). Состав вершин — `graph_node`: без него город без рёбер выпал бы
из анализа, хотя изолированность — тоже результат.

### graph_edge — ребро графа

| Поле | Тип | NULL | Смысл и ограничения |
|---|---|---|---|
| graph_edge_id | uuid | нет | PK |
| graph_snapshot_id | uuid | нет | FK → `graph_snapshot` |
| from_city_id, to_city_id | uuid | нет | Вершины этой же версии (FK → `graph_node`); города разные |
| transport_type | text | нет | Вид транспорта или `multimodal` |
| weight | numeric | нет | `> 0`; стоимость — меньше значит лучше |
| weight_unit | text | нет | `sec` или `m` |
| measurement_id | uuid | да | FK → `route_measurement`, на котором основано ребро |

Одно ребро на `(graph_snapshot_id, from_city_id, to_city_id, transport_type)`.

### analysis_run и metric_result — расчёты

`analysis_run` — один запуск алгоритма на версии графа: алгоритм, движок и его версия,
параметры, сценарий (например, удалённые рёбра; `NULL` — исходный граф), commit, статус.
`metric_result` — значения: показатель, город, второй город для показателей пары
(время A → B) и число. `NULL` в значении — «не определено», например город недостижим.
Так результат из Neo4j возвращается в PostgreSQL вместе с условиями, при которых получен.

## Будущие сущности

Появятся вместе со своими задачами; сейчас зафиксированы назначение и ключ.

| Сущность | Зачем | Ключ и связи |
|---|---|---|
| `road_segment` | Участки дорог OSM с геометрией | `uuid5` от снимка и OSM way id; `geometry(LineString, 4326)` |
| `station` | Вокзалы, аэропорты, автостанции | Код станции у источника; FK → `city` (пусто до сопоставления); часовой пояс |
| `transport_connection` | Рейс из расписания на дату | Две станции, отправление и прибытие в UTC; ключ рейса — [#15](https://github.com/AlexKeyyyy/transport-connectivity/issues/15) |

## Пример: реальная строка

Строка 2 файла `data/samples/intercity_connectivity_sample.csv`:

```text
Брянск;Брянская область;15701000001;953;1;379152;53.2420053;34.3653002;
Владимир;Владимирская область;17701000001;986;1;349951;56.1280444;40.4082983;
road;694.0;9.8;CD;OSM;CD
```

| Таблица | Что записывается |
|---|---|
| `data_snapshot` | `tochno_intercity_v20260629` |
| `city` | Брянск: `city_id = 83c80e94-954a-5182-b2dd-a4aa219e6400` (из Sber ID `953`), Брянская область, 379 152 чел., `POINT(34.3653002 53.2420053)` |
| `city` | Владимир: `city_id = 7e9d63d7-2778-54ed-bd76-e000209493d6` (из Sber ID `986`) |
| `city_external_id` | (`sber_territory`, `953`), (`oktmo`, `15701000001`) → Брянск; так же для Владимира |
| `route_measurement` | `fb7e015a-513c-5f3b-849a-a5a886ad08a8`, строка 2, `road`, 694 000 м, 35 280 с, причина `CD`, источник `OSM` |

Для той же пары самолётом источник даёт пустые числа и «Маршрут не найден»: запись
сохраняется с `NULL` в расстоянии и времени. Идентификаторы посчитаны по формулам контракта.

## Neo4j и Elasticsearch

**Neo4j** получает одну версию графа со статусом `ready`: вершина `(:City {city_id, name,
region, population})` на каждую запись `graph_node`, связь `[:CONNECTED {transport_type,
weight, weight_unit}]` на каждое ребро. Результаты алгоритмов записываются обратно
в `analysis_run` и `metric_result`.

**Elasticsearch** — индекс `cities` для поиска города по названию с опечатками и рядом
с точкой. Mapping — в задаче поиска ([#5](https://github.com/AlexKeyyyy/transport-connectivity/issues/5)).

| Поле | Откуда | Тип |
|---|---|---|
| `city_id` | `city.city_id`, он же `_id` | keyword |
| `name` | `city.name` | text + keyword |
| `aliases` | Другие написания из OSM и Яндекса | text |
| `region` | `city.region` | keyword |
| `population` | `city.population` | integer |
| `location` | `city.location` | geo_point |

## Что решим позже

- Методику графа: смысл ребра, вес, сценарии устойчивости.
- Сопоставление OSM-объектов городам — до него данные OSM и OSRM пилота в модель не грузятся.
- Ключ рейса расписаний (#15).
- Историю атрибутов города: сейчас хранится значение из последнего снимка; при втором
  снимке того же источника атрибуты выносятся в таблицу по снимкам.
- Перезагрузку снимка, на котором уже построен готовый граф: пока она запрещена,
  новая версия контракта даёт новую загрузку и новую версию графа.
