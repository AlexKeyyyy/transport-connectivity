# Как вносить изменения

## Ветки и запросы на слияние

1. Прочитайте задачу и зафиксируйте, какой результат можно проверить.
2. Создайте ветку `feature/<номер>-<тема>` от актуального `develop`.
3. Сделайте коммиты по отдельным изменениям. Для заголовка используйте
   `feat:`, `fix:`, `docs:`, `test:`, `refactor:` или `chore:`.
4. Откройте PR в `develop`. Опишите результат, команды проверки и известные
   ограничения. Слияние выполняется после рецензирования и успешного CI.

В `main` через PR попадают выпуски с тегами. Существенные изменения
архитектуры фиксируйте в [ADR из указателя документации](README.md).

## Код и данные

- Используйте Python 3.12+, понятные имена и аннотации типов для публичных
  функций. Сохраняйте преобразования и расчёты отдельно от сетевого,
  файлового ввода-вывода и SQL.
- Для входных данных указывайте источник, снимок, единицы и правила
  обработки пропусков. Храните внешние идентификаторы вместе с источником.
- Проверяйте баланс записей и повторный запуск. Не публикуйте частичный
  результат как готовый. Большие выгрузки, дампы и ключи оставляйте вне Git.
- При изменении схемы, идентификаторов или формата результата обновите
  затронутые тесты и документацию в том же PR. Схему и миграции проверяйте
  на отдельной тестовой базе.

## Проверка

```bash
python -m pip install -e ".[dev]"
python scripts/dev/check.py
```

Эта команда проверяет ссылки документации, стиль, форматирование и тесты.
Интеграционные проверки запускайте на отдельных сервисах. Параметры
подключения описаны в руководствах по
[PostgreSQL](../data/README.md#загрузка-в-базу), [Neo4j](neo4j.md) и
[Elasticsearch](elasticsearch.md). Для проверки полного сценария
используйте [инструкцию запуска](../README.md#воспроизвести-проверенный-сценарий).
