# Поиск городов: индекс Elasticsearch

Статус: **проект, PoC не запускался.** Mapping и запросы ниже ещё не выполнялись на
сервере. Ожидаемые ответы посчитаны по нормализованному `cities.csv` (180 городов,

## Роль в системе

Elasticsearch — производный индекс, а не справочник. Источник истины — таблица `city`
в PostgreSQL ([модель данных](data-model.md#neo4j-и-elasticsearch)): индекс
пересобирается из неё целиком, исходные данные под индекс не меняются. Задача индекса —
найти `city_id` по тому, что ввёл человек: точное название, начало названия, название
с опечаткой, город в регионе, города рядом с точкой.

## Mapping

Поля — из модели данных. `dynamic: strict` запрещает поля, которых нет в mapping.

```json
PUT cities_v1
{
  "settings": {
    "analysis": {
      "char_filter": {
        "yo_to_e": { "type": "mapping", "mappings": ["ё => е", "Ё => Е"] }
      },
      "tokenizer": {
        "prefix_tokenizer": {
          "type": "edge_ngram", "min_gram": 2, "max_gram": 20,
          "token_chars": ["letter", "digit"]
        }
      },
      "analyzer": {
        "city_name": {
          "type": "custom", "tokenizer": "standard",
          "char_filter": ["yo_to_e"], "filter": ["lowercase"]
        },
        "city_prefix": {
          "type": "custom", "tokenizer": "prefix_tokenizer",
          "char_filter": ["yo_to_e"], "filter": ["lowercase"]
        }
      }
    }
  },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "city_id":    { "type": "keyword" },
      "name": {
        "type": "text", "analyzer": "city_name",
        "fields": {
          "keyword": { "type": "keyword" },
          "prefix":  { "type": "text", "analyzer": "city_prefix", "search_analyzer": "city_name" }
        }
      },
      "aliases":    { "type": "text", "analyzer": "city_name" },
      "region":     { "type": "keyword" },
      "population": { "type": "integer" },
      "location":   { "type": "geo_point" }
    }
  }
}
```

Почему так:

- **`city_id` — `keyword` и он же `_id` документа.** Повторная загрузка перезаписывает документ, а не создаёт дубль.
- **`ё → е` при индексации и поиске.** В наборе есть Орёл, Королёв, Щёлково; человек обычно пишет «Орел».
- **`name.prefix` — частичный ввод.** `edge_ngram` индексирует начала слов («ни», «ниж», «нижн»…), а запрос анализируется обычным анализатором, чтобы «Нижн» не разбивался на n-граммы.
- **`name.keyword` — точное совпадение** и сортировка.
- **`region` — `keyword`:** регион используется как точный фильтр, а не для полнотекстового поиска.
- **`location` — `geo_point` объектом `{lat, lon}`:** так нельзя перепутать порядок, как в массиве `[lon, lat]`.
- **`aliases`** — другие написания (OSM, Яндекс). Пока пусто: сопоставление OSM и Яндекса с городами ещё не сделано.

Документ для Брянска:

```json
PUT cities_v1/_doc/83c80e94-954a-5182-b2dd-a4aa219e6400
{
  "city_id": "83c80e94-954a-5182-b2dd-a4aa219e6400",
  "name": "Брянск",
  "aliases": [],
  "region": "Брянская область",
  "population": 379152,
  "location": { "lat": 53.2420053, "lon": 34.3653002 }
}
```

Загрузка — пакетом через Bulk API с проверкой ошибки **каждого** элемента ответа: код 200 всего запроса не значит, что проиндексированы все документы.

## Запросы и ожидаемые ответы

| № | Сценарий | Запрос | Ожидаемый ответ (Sber ID) |
|---|---|---|---|
| 1 | Точное название | `term` по `name.keyword`: «Брянск» | Брянск (953) |
| 2 | Начало названия | `match` по `name.prefix`: «Нижн» | Нижний Новгород (1523), Нижний Тагил (2000), Нижневартовск (2221), Нижнекамск (385) |
| 3 | Опечатка | `match` по `name`, `fuzziness: AUTO`: «Брянкс» | Брянск (953) |
| 4 | «е» вместо «ё» | `match` по `name`: «Орел» | Орёл (1707) |
| 5 | Город в регионе | `match` по `name` + `filter` `term` по `region`: «Королев», «Московская область» | Королёв (1456) |
| 6 | Рядом с точкой | `geo_distance` 25 км от Москвы (55.7540584, 37.62049), сортировка по расстоянию | 11 городов: Москва (0 км), Реутов (15), Люберцы, Мытищи, Химки (19), Балашиха, Красногорск (20), Долгопрудный (22), Видное, Королёв (23), Одинцово (24) |

Расстояния в п. 6 посчитаны по формуле гаверсинусов (радиус Земли 6 371 км) и округлены до километра; Elasticsearch считает свою дистанцию, и город на границе радиуса может попасть или не попасть — для проверки берём радиус, где ближайший город за границей заметно дальше (Щёлково, 29 км).

Запрос 3 — опечатка «Брянкс» отличается от «Брянск» перестановкой соседних букв: при `fuzzy_transpositions` (включено по умолчанию) это одна правка, а слово из 6 букв допускает две ([fuzziness](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/common-options)).

```json
GET cities_v1/_search
{ "query": { "match": { "name": { "query": "Брянкс", "fuzziness": "AUTO" } } } }
```

```json
GET cities_v1/_search
{
  "query": {
    "bool": {
      "must":   { "match": { "name": "Королев" } },
      "filter": { "term":  { "region": "Московская область" } }
    }
  }
}
```

```json
GET cities_v1/_search
{
  "size": 20,
  "query": {
    "bool": {
      "filter": {
        "geo_distance": { "distance": "25km", "location": { "lat": 55.7540584, "lon": 37.62049 } }
      }
    }
  },
  "sort": [
    { "_geo_distance": { "location": { "lat": 55.7540584, "lon": 37.62049 }, "order": "asc", "unit": "km" } }
  ]
}
```

## Что сделать в PoC

1. Поднять Elasticsearch той версии, что выберем для проекта, и проверить, что встроенных анализаторов хватает (плагины не нужны).
2. Создать `cities_v1`, загрузить 180 городов из PostgreSQL (до появления БД — из `cities.csv`) через Bulk с проверкой каждого элемента.
3. Выполнить шесть запросов и сравнить ответы с таблицей: проверяются состав и порядок, а не «ответ не пустой».
4. Для пересборки без простоя — алиас `cities` на `cities_v1`; новая версия индекса собирается рядом и переключается после проверки. Для учебного PoC достаточно одного индекса.
