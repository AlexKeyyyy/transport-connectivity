# AGENTS.md — правила для coding-агентов

## Перед работой

1. Прочитай текущий Issue целиком, README и относящиеся к задаче документы.
2. Проверь Git status и изменения пользователя. Работай в отдельной ветке
   от актуального main: `feat/<issue>-<short>`, `fix/...`, `docs/...`, `research/...`.
3. Определи минимальное изменение для Acceptance Criteria. Следующие этапы
   и неподтверждённые гипотезы не включай в текущую реализацию.
4. Явные инструкции пользователя имеют приоритет; при изменении архитектурного
   решения обнови связанные документы и запиши значимое решение в ADR.

## Выбор skills

- Issue и передача работы: `$transport-task`; ETL/коннектор: `$transport-data-pipeline`.
- PostgreSQL: `$supabase-postgres-best-practices`; пространственные операции: `$transport-postgis`.
- Методика/сценарии графа: `$transport-graph-methodology`; проекция и GDS: `$transport-neo4j`.
- Поиск cities: `$transport-elasticsearch`; notebook: `$jupyter-notebook`.
- Перед сдачей используй `$transport-verify`. Читай только нужные skills/references.
- Skills установлены в `.agents/skills/`; происхождение и адаптации — `.agents/skills-lock.json`.
  Не устанавливай runtime-зависимости или сервисы только из-за примера в skill.
- Установленные версии и реальные контракты важнее чужих общих примеров.
  Уже данное пользователем разрешение на действие не требует повторного запроса из-за skill.

## Архитектура

- Следуй [docs/architecture.md](docs/architecture.md) и контракту текущей задачи.
- PostgreSQL/PostGIS — основное хранилище нормализованных данных и результатов.
- Neo4j — производный граф, Elasticsearch — производный индекс; оба восстанавливаются
  из PostgreSQL. OSRM строит routing dataset из закреплённого OSM snapshot.
- Один Python-пакет с модулями по ответственности. Новые сервисы, библиотеки,
  интерфейсы и слои добавляй при конкретной необходимости, объясняя её в PR.
- Преобразования и расчёты отделяй от HTTP, SQL и файлового ввода/вывода.
  Не создавай базовые классы, универсальные repositories, очереди и плагины заранее.
- Каталоги появляются вместе с кодом. Сервис и его инфраструктура — в своём Issue.

## Корректность данных

- У данных известны источник, снимок, единицы, CRS и правила пропусков.
- Внешний ID хранится вместе с источником. Название города не является ключом.
- RouteMeasurement не становится GraphEdge без описанной методики.
- У алгоритма определены тип графа, смысл веса и допустимые сценарии.
- Отсутствие маршрута, отсутствие запроса и ошибка источника различаются.
- Повторный запуск не создаёт дубликаты. Ошибки и отклонённые строки учитываются;
  частичный результат не публикуется как готовый. Сохраняй баланс входа и выхода.

## Код и проверки

- Python 3.12+, пакет `src/transport_connectivity/`, конфигурация `pyproject.toml`.
- Добавляй зависимости только для реализуемой задачи. Используй type hints
  в публичных функциях и понятные имена; комментарии объясняют причины решений.
- Тестируй значимое поведение: преобразования, единицы, пропуски, ID, ошибки,
  повторный запуск. Маленькие fixtures; live API не нужны для обычного pytest.
- БД и миграции проверяй интеграционно, когда они появляются.
- Запускай `python scripts/dev/check.py` (harness, Ruff, pytest) и проверки текущего Issue.
  Для документации проверь ссылки и согласованность. Не выдавай smoke-тесты за
  подтверждение корректности полного pipeline.

## Данные и секреты

- Большие CSV, PBF, дампы, OSRM datasets, индексы ES и БД Neo4j в Git не добавляются.
  В Git допустимы маленькие samples, fixtures и отчёты. Raw/processed — игнорируются.
- Секреты передаются через environment variables; `.env` игнорируется,
  `.env.example` содержит только имена и безопасные примеры.
- Не записывай абсолютные пути разработчика и секреты в код, логи или manifest.

## Issues, PR и завершение

- Одна задача — одна цель; короткое описание: цель, сделать, готово, зависимости.
  Общие инструкции не дублируй. Не назначай сроки без договорённости.
- Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`.
- Проверь все Acceptance Criteria. Новые самостоятельные проблемы вынеси отдельно.
- В PR: что изменилось, как проверить, результаты проверок и существенные ограничения.
- В итоговом отчёте: сделанное, изменённые файлы, проверки, решения и нерешённое.
- Skills выбирай по задаче из [docs/skills.md](docs/skills.md); они не заменяют
  требования проекта и проверку по документации библиотек.
