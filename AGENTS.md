# AGENTS.md — правила для coding-агентов

## Перед кодом

1. Прочитай текущий GitHub Issue целиком — это основное ТЗ итерации.
2. Изучи структуру репозитория, README и `docs/`.
3. Определи минимальный набор изменений для выполнения Issue.
4. Не реализуй то, что не требуется текущим Issue
   (OSM ingestion, OSRM, Neo4j, Elasticsearch, API — только когда будет свой Issue).

## Архитектура

- PostgreSQL + PostGIS — основной source of truth (нормализованные данные).
- Neo4j — производное графовое представление для алгоритмов.
- Elasticsearch — производный поисковый индекс.
- Состояние Neo4j/Elasticsearch должно восстанавливаться из PostgreSQL.
- Не меняй эти решения без явного обсуждения; важные решения фиксируй в `docs/adr/`.

## Границы

- Не создавай пустые папки ради структуры.
- Большие данные не коммитятся: `*.osm.pbf`, дампы БД, файлы OSRM,
  индексы ES, БД Neo4j, большие CSV. Допустимы лишь маленькие файлы в `data/samples/`.
- Секреты только через environment variables. В git — только `.env.example`, никогда `.env`.
- Без абсолютных путей к машине разработчика; воспроизводимость важнее удобства.

## Python

- Python 3.12+, пакет в `src/transport_connectivity/`, конфиг в `pyproject.toml`.
- Зависимости добавляй только когда реально нужны (сейчас: pytest, Ruff).
- Type hints там, где разумно; новая функциональность — с тестами.

## Git

- Никогда не работай напрямую в `main`.
- Ветка от актуального `main`: `feat/<issue>-<short>`, `fix/...`, `docs/...`, `research/...`.
- Commits: `feat: ...`, `fix: ...`, `docs: ...`, `test: ...`, `refactor: ...`, `chore: ...` (по-русски допустимо).

## Завершение

- Проверь Acceptance Criteria Issue; невыполненное требование = задача не готова.
- Новую отдельную проблему не раздувай в текущем PR — предложи её как отдельный Issue.
- Запусти `pytest` и `ruff check`; сравни результат с критериями готовности.
- Отчёт в конце: что сделано, какие файлы изменены, как проверить,
  принятые решения и допущения, что осталось нерешённым.
